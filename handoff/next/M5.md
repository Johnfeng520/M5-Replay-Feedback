# M5 · 下一阶段主线：规则回放、节点反馈、版本统计

基线：integration/m4-stage-20261102。计划按交付顺序推进，不虚构尚未约定的日期。

## 已有基础，直接扩展

`modules/events` 已有 appendEvent、findChoiceReceipt、readEventStream；M2 的状态和事件在同一真实事务提交。sharing 与 events HTTP 接口、权限隔离已实现。正常/恢复/缺失/乱序/篡改样例仍在 fixtures/events。完整回放、反馈、统计四个路由尚未实现，这是你的下一阶段主要交付。

## 第一批：完整规则回放（先交）

实现 GET /sessions/:id/replay。先在同一事务用 `player.readForReview(tx,actorId,id)` 验证本人或对应活动作者且分享有效，再读固定版本与事件。起点为 session.initialState，从 seq=1 连续到 finalSeq；每步核对 before，经唯一 applyChoice 算 after/delta，再核对记录，最后与会话 state/seq 一致。发现缺失/乱序/篡改/规则不符返回契约 MISMATCH 与位置，不跳过、不自动修复。恢复分支从自己的 initialState 开始，原会话来源只作为追溯信息。

## 第二批：真实节点反馈

实现 POST /sessions/:id/feedback、GET /activities/:id/feedback?versionId=...。仅玩家本人且明确分享才能提交；eventSeq=0 对应 initialState，其余对应事件后的状态；服务器重新核对 nodeId、versionId、序号和归属。使用 Feedback 已有唯一约束、requestHash、requestId 做幂等。作者读取必须属于本人活动/指定版本并且当前分享仍有效。页面可在真实步骤提交反馈，作者可跳到该状态。

## 第三批：按版本统计与作者界面

实现 GET /activities/:id/summary?versionId=...。只统计对应活动/版本、当前分享有效的会话；初始状态一次访问，每个事件 after 一次访问；结束会话一次结局。恢复会话是独立分支，其 source 不等于额外重算原会话事件。撤销分享后回放、反馈读取和统计统一排除。与 M1 接作者工作区，提供版本选择、路径/状态、反馈定位。

## 接口与数据交接

Rule/Version/Event 端口见 `api/src/ports.ts`，HTTP 和 Replay/Feedback/Summary 模型见 OpenAPI。需要 tx 的地方复用 M4 transact；appendEvent 不另建客户端、不吞异常。反馈是本域数据，不能改玩家 state、Story 或固定版本。

每批交给 M2/M4：新 commit、基线 hash、涉及接口、实际测试和一条浏览器路径。先回放，再反馈，最后统计，允许逐批合入；不要等所有界面都做完才首次联调。

## 完成条件与门禁

正常和恢复分支逐步一致；缺失/乱序/篡改均可定位且不伪报通过；默认未授权的作者查询拒绝；开启后可读，撤销后后续查询及统计排除；反馈不能绑定错步骤、错节点或别人的会话；两版本统计不混。每项有实际 API 测试和 UI 证据，`npm run verify` 全过，由 M2 验规则、M1 验入口、M4 验权限和集成后接收。
